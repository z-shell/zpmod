# zpmod benchmarks

The benchmark harness measures end-to-end Zsh startup time for one generated, parse-heavy workload under four conditions:

| Case            | What it measures                                                         |
| --------------- | ------------------------------------------------------------------------ |
| Plain source    | Uncompiled files loaded without zpmod                                    |
| zpmod first run | No `.zwc` files exist, so automatic compilation cost is included         |
| zpmod warm      | `.zwc` files generated by an earlier zpmod run are reused                |
| Manual `.zwc`   | Native Zsh control, compiled before measurement and loaded without zpmod |

The manual control separates the benefit of Zsh bytecode from zpmod's automation and interception overhead. Cases run in a balanced rotating
order to reduce time-dependent bias. Each child shell uses `zsh -f` with isolated `HOME` and `ZDOTDIR` directories.

## Run a benchmark

Build and stage zpmod first, then run:

```zsh
scripts/cmake.configure.zsh --generator ninja --build-type Release

zsh -f benchmarks/run.zsh \
  --module-dir build-cmake/stage/lib/zsh/site-modules \
  --output-dir benchmark-output \
  --source-revision "$(git rev-parse HEAD)" \
  --environment "local Linux x86_64"

zsh -f benchmarks/render.zsh \
  --input benchmark-output/benchmark.tsv \
  --svg benchmark-output/benchmark.svg \
  --markdown benchmark-output/benchmark.md
```

`run.zsh` emits raw JSON and a renderer-oriented TSV file. `render.zsh` creates an accessible SVG and a Markdown report with the exact data
table.

Use `--compiler` when benchmarking a prebuilt module whose build compiler is different from the compiler installed on the measurement host.
Use `--cpu` to override CPU detection when a virtualized runner exposes an inaccurate label.

## Interpret results carefully

- The fixture is synthetic. It isolates parsing and compilation behavior but does not represent every real Zsh setup.
- "First run" means the workload starts without `.zwc` files. It does not mean the operating-system filesystem cache was cleared.
- Hosted CI runners can vary in hardware and load. Their results are useful as downloadable evidence, but they are not a blocking
  performance regression gate.
- Compare results only when the workload, Zsh version, module revision, architecture, and environment metadata are compatible.
- Do not turn one result into a universal "N times faster" claim.

## Published evidence

Versioned result directories contain the raw JSON and TSV data plus generated SVG and Markdown views. The committed v2.0.6 Linux result was
measured from the SHA-256-verified release archive and identifies the exact release commit, module hash, workload, host, and sample counts.

- [v2.0.6 Linux x86_64 report](results/v2.0.6-linux-x86_64/benchmark.md)
- [v2.0.6 raw JSON](results/v2.0.6-linux-x86_64/benchmark.json)

The `Benchmark` GitHub Actions workflow also supports manual and published release runs. It uploads raw and rendered outputs as non-gating
workflow artifacts; publishing a new committed result remains a reviewed source change.
